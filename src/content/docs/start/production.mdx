This page takes the [quick start](/start/quickstart/) install and makes it fit to keep. You add TLS, back up the three places Codex stores data, pin an image version and size the host for print runs.

## Add TLS with Caddy

Codex listens on plain HTTP on port 8080. Put a reverse proxy in front of it that holds the certificate. The example below uses Caddy, which gets and renews a certificate for your domain by itself.

Codex marks its sign-in cookie Secure when the request it sees is HTTPS. Behind a proxy the app sees HTTP, so the proxy must send `X-Forwarded-Proto` and `X-Forwarded-Host`. The Caddyfile sets both. Without them, the cookie is not marked Secure even though the browser uses HTTPS.

1. Point a DNS record for your domain at the machine. Open ports 80 and 443 on its firewall.
2. Make a folder named `caddy` beside your `docker-compose.yml`. Save the two files below into it.
3. Add `CODEX_DOMAIN=codex.example.com` to your `.env`, with your own domain.
4. Start the stack with both compose files.

```sh
docker compose -f docker-compose.yml -f caddy/docker-compose.yml up -d
```

The second file removes the published port 8080 from the app, so only Caddy reaches it. Port 80 must stay open, because Caddy uses it to prove to the certificate authority that you own the domain. Keep the `caddy-data` volume, or Caddy asks for new certificates on every start.

The files are in the docs repository: [Caddyfile](https://github.com/codexsuite/docs/blob/main/examples/caddy/Caddyfile) and [docker-compose.yml](https://github.com/codexsuite/docs/blob/main/examples/caddy/docker-compose.yml).

```txt title="caddy/Caddyfile"
{caddyfile}
```

```yaml title="caddy/docker-compose.yml"
{caddyCompose}
```

Caddy sets these headers itself and ignores any copy a client sends. The `header_up` lines state them so the file shows what Codex needs. For Caddy's own options, see its [reverse_proxy reference](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy). Another proxy works if it sends the same two headers.

Check the result with `curl https://codex.example.com/health`. It answers `{"status":"ok","version":"..."}` and needs no sign-in.

## What to back up

Codex keeps data in three places. A backup of one without the others does not restore a working install.

| Store | Where it lives | What it holds |
|---|---|---|
| Postgres | The `codex-pgdata` volume | Books, scenes, sources, users, sign-in sessions and the keys that sign the session cookie. |
| Blob folder | The `codex-blobs` volume, mounted at `CODEX_BLOB_ROOT` | Uploaded files, image renditions and exports. |
| Key ring | The `codex-keys` volume, mounted at `CODEX_DATA_PROTECTION_DIR` | The keys that encrypt the AI keys users save. |

Back up all three at the same time, and keep the key ring apart from the database dump. The key ring is meant to live outside the database, so that a dump alone cannot decrypt anyone's AI key.

To dump the database:

```sh
docker compose exec -T postgres pg_dump -U postgres -d codex --format=custom > codex.dump
```

To copy a volume to a tar file, run a throwaway container that mounts it. Compose prefixes volume names with the project name, so list them first with `docker volume ls`.

```sh
docker run --rm -v <project>_codex-blobs:/data:ro -v "$PWD":/backup alpine tar -czf /backup/codex-blobs.tgz -C /data .
docker run --rm -v <project>_codex-keys:/data:ro -v "$PWD":/backup alpine tar -czf /backup/codex-keys.tgz -C /data .
```

To restore, stop the stack, put the three stores back, and start it again. A restored database without its key ring still opens. Only the saved AI keys are lost.

### If you lose the key ring

Codex cannot read the AI keys it saved with a key ring it no longer has. Nothing else breaks. When someone drafts with AI or presses Test on an integration, Codex answers `not_configured` with the message "The saved key can't be read with this server's key folder. Enter the key again in Settings → AI." Each user opens Settings, then AI, and enters the key again.

Users can also back up one book from inside the app. That backup holds the book, not the install, so it does not replace the three stores above.

## Upgrade

The images have two tags, `latest` and the full commit SHA of the build. `latest` moves on every build, so a production file that uses it upgrades on whichever day you next pull. Pin a SHA instead.

1. Back up the three stores.
2. Pick a build. The running app reports its commit: `curl https://codex.example.com/health` returns a version such as `1.0.0+35618f3...`. The part after the plus sign is the commit. Tags on [the app image page](https://github.com/codexsuite/codex/pkgs/container/codex) list the builds.
3. Set the same SHA for both images in `.env`:

```sh
CODEX_IMAGE=ghcr.io/codexsuite/codex:<full commit SHA>
CODEX_WORKER_IMAGE=ghcr.io/codexsuite/codex-worker:<full commit SHA>
```

4. Run `docker compose pull` and then `docker compose up -d`.

Use the same SHA for the app and the worker, because they share one database schema and one set of job rules. The web service applies database migrations when it starts, and the worker does not (`CODEX_DB_MIGRATE=false`). After an upgrade the worker can start before the web service has finished migrating. Its job loop logs the error and tries again every 2 seconds, so it recovers by itself once the schema is current.

To go back, set the older SHAs and run the same two commands. Migrations are not reversed, so restore the database backup from before the upgrade when the newer version changed the schema.

## Run more than one web host

Run one `codex` service. Live updates between processes go through a Postgres notification bridge. The product documents that bridge for two cases only: edits from the worker and from the stdio MCP server reaching the web host. It does not describe web host to web host, so nothing here promises that several web hosts show each other's changes. Blob storage is also one folder on one disk, so extra web hosts would need a shared disk.

## Size the host

Codex does not state a memory or CPU minimum. These figures come from the code and the defaults:

- A print run for a proof or an export for the printer runs Tectonic in a sandbox. Codex caps its address space at 4 GiB, so keep at least that much free memory for the worker when a book is large.
- One run may take 300 seconds (`CODEX_RENDER_TIMEOUT_SECONDS`) and may write a PDF of up to 1024 MB (`CODEX_RENDER_MAX_PDF_MB`). Lower the limits to fail a runaway run sooner.
- One worker runs one export and one proof at a time, and polls for new jobs every 2 seconds. Exports queue behind each other. A longer book makes each run longer, and a second worker is the way to run more at once.
- The worker container writes each run under `CODEX_RENDER_WORK`, which defaults to the container's temp folder. Keep enough free disk for the largest PDF.
- Postgres needs the usual headroom for its cache. The database holds text, so it stays small beside the blob folder.

Printing also needs a Linux kernel with Landlock ABI 4, which arrived in Linux 6.7. See the [requirements](/start/requirements/) for the command that tests your host.
